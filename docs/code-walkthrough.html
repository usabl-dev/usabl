01

The short answer

One pipeline. One decision-maker.

The engine is about 83 source files and more than 11,000 lines of TypeScript in src/. A separate test folder mirrors it, with another 14,000 lines and more than 600 automated tests. Every source file has one of three jobs: collect evidence, make the one decision, or show that decision to people.

This page explains the code in the order it runs. One tip before you start: every file begins with a short comment. The comment says what the file does and what it must never do. The most common "must never" is: never decide the final answer. Only one module can do that. It is called the gate.

The main design rule: checks produce evidence. The gate turns the evidence into one final answer, called the verdict. All other code only displays the verdict. If any other code produces its own answer, that is a bug, even when the answer happens to be correct.

02

Contracts, deps, and run

Three files form the core. Everything else connects to them.

src/contracts/index.ts defines the shared data shapes. src/deps/ holds all code that touches the outside world. src/run.ts controls the order of the steps.

  1. Check the policy filesThe guard compares the tool's own policy files with a trusted copy in git. If any differ, the run stops here and asks for human approval.
  2. Read changed filesrun() gets the list of changed files from the caller, or asks git for local changes.
  3. Plan coverageThe planner finds which screens the changed files affect. "Coverage" means: the set of screens the tool must check.
  4. Scan the screensThe check runner opens each affected screen in a browser and runs every check.
  5. Decide, then recordThe gate produces the verdict. Only a "verified" verdict creates a receipt.

One interface for the outside world

contracts/index.ts defines Deps: file access, git access, the browser, and the clock, all in one object. run() receives this object as an argument. No other code opens files or starts a browser on its own. Because of this one rule, the whole engine can run inside a test.

A real version and a test version

deps/real.ts uses a real browser (Playwright with Chromium). It reads element names from the browser's accessibility tree. That tree is the same data a screen reader uses, so the engine sees what a screen reader user gets. deps/fakes.ts is a copy that works only in memory; the tests use it. If a test calls a fake method that was not set up, the fake throws an error. This makes hidden test mistakes visible instead of letting them pass.

Core rule: run() only controls the order of steps. It never decides the verdict. If the engine crashes, the result is exit code 4, no verdict, and a clear error message. A crash can never produce "verified".

03

src/coverage/

Coverage answers one question: which screens must be checked?

Three files do this work. When they cannot connect a changed file to a screen, they record a gap. A gap means: something changed and the tool could not check it. Any gap turns the verdict into "not covered".

route-manifest.ts

Reads usabl.routes.json, the file that lists the pages (routes) of the app. If that file is missing, a fallback reads the router source code and finds the route paths. The fallback cannot know which component draws each route, so it leaves that field empty instead of guessing.

import-graph.ts

Starts from each route's main file and follows its imports. The result is the list of files each screen depends on. It follows only imports it can find on disk. Anything it cannot resolve is recorded, not guessed.

planner.ts

Connects changed files to screens in three ways: through the import graph, through wide-impact patterns, and through manual mappings in the config. A wide-impact file, such as a stylesheet used everywhere, marks every screen as affected, because its real reach cannot be proven smaller.

Idle is honest

If no interface file changed, the run is idle: no verdict, exit code 0, and the message "nothing to check". Idle means there was nothing to prove. It is not a pass.

Unmapped means a gap

If an interface file changed and no screen could be found for it, the planner writes a gap with a reason. The gate then returns "not covered". Nothing is dropped in silence.

Coverage rule: no sampling. The tool checks every affected screen, or it states clearly what it could not check.

04

src/trust/, src/intake/

The trust code expects that anyone can edit any file.

The engine runs in a workspace where an AI assistant edits files. The assistant can also edit the engine's own policy files: the config, the route list, the accepted-findings list, and the waiver list. The trust layer makes sure a policy change can never approve itself. This check runs before everything else, so a broken or damaged policy file blocks the run instead of crashing it.

  1. 1. Config first Compare the bytes of usabl.config.json with the trusted copy in git before using anything written inside it.
  2. 2. Verified bytes only The list of guarded files comes from the checked config bytes, never from data already in memory.
  3. 3. Expand folders A guarded folder becomes a list of its files, both committed files and new files. A new file cannot hide inside a guarded folder.
  4. 4. Compare every file Every guarded file is compared byte by byte with the trusted copy in git.
  5. 5. Any change blocks If even one guarded file differs, the verdict is "approval required". A person must review it. No scan runs.

Intake stops on bad input

intake/ reads requirement files that the team writes in YAML. The parser uses a safe mode, so YAML cannot create unexpected object types. The validator rejects unknown fields instead of ignoring them, and it rejects invalid dates in waivers. One broken file means "approval required", because a rule set must never be applied halfway.

Requirements become checks

intake/map-to-providers.ts turns written requirements into runtime checks: required announcements, keyboard paths, image descriptions. Documentation requirements do not become checks; they describe output files instead.

Why compare bytes instead of reading the content? Reading a changed file means trusting a changed file. The guard only reports that bytes are different. It never repairs, excuses, or interprets the difference. Interpretation is a human job.

05

src/providers/ and src/voicing/

Providers collect evidence. They are not allowed to conclude.

A provider is one check. It returns drafts and gaps. A draft is one observation: what the user experiences, why it matters, and a possible fix. providers/check-runner.ts opens one screen, records a keyboard pass, then runs every provider. It never throws an error: a screen that fails to open or scan becomes a gap, never a silent skip.

axe/

Runs axe-core, a widely used open-source accessibility scanner, and turns its results into drafts. When axe is not sure about a result, the draft is marked "unverified". Unsure results are kept, not dropped. They push the verdict toward "not covered".

rulepack/

Six checks written for PatternFly, the design system used by the demo app: icon button names, menu open-and-closed state, unique row actions, table headers, toast placement, and repeated toolbars. It also contains probes: small scripts that really open a dialog or a menu and watch where keyboard focus goes.

keyboard-walk/

Presses the Tab key through the screen and records every stop: the name, role, and state of each element. It stops when the cycle repeats. It reports interactive controls that have no name. When data is missing from the accessibility tree, the draft says "unverified". It never guesses.

Voicing: built and exported, not yet wired in

The voicing lane is built and exported from the library, but v0.2.0 does not import it into the run path, so it does not affect the gate yet. It has two parts. voicing/structural.ts checks facts: did an announcement happen at the required moment, yes or no. Those drafts are deterministic, which means repeatable and machine-checked. voicing/voicing.ts compares the words of the announcement. Word matching is weaker evidence, so those drafts would be marked "preview" by default. A human can promote a word rule to a blocking rule in config, and the code never promotes itself. The lane and its calibration land in v0.3.0.

How announcements are captured

The real browser driver installs a small observer script before the page loads. When the page writes into a live region, which is the area a screen reader announces out loud, the observer records a token. The checks compare these tokens with the written requirements. This is how the tool catches a toast message that appears on screen but is never announced to a screen reader user.

Evidence rule: every draft carries one of four evidence classes: "deterministic", "preview", "model-judgment", and "human-confirmed". Only "deterministic" drafts can change the verdict. "Preview", "model-judgment", and "human-confirmed" drafts are shown to people, but they can never create "verified" or a receipt.

06

src/gate/, src/primitives/identity.ts, src/evidence/

The gate turns drafts into findings, and findings into one verdict.

This is the only module that makes the decision. It receives everything as input: the coverage, the guard result, the drafts, the accepted-findings list, the waivers, and the clock. It performs no input or output of its own.

Identity: same problem, one finding

primitives/identity.ts builds a key for each finding. It prefers the element's accessible name, because a name survives layout changes. Without a name it uses the element's role and position. As a last resort it counts occurrences. The key ignores which provider found the problem, so when axe and a PatternFly rule report the same defect, they merge into one finding.

Status: compare with the accepted list

The evidence floor is the list of findings the team has already accepted. A finding on the list is "carried" and does not block. A finding not on the list is "new" and blocks. A listed finding that no longer appears becomes "fixed": still shown, never blocking. Waivers are written exceptions with a validated expiry date. Together this lets a team block new problems without claiming old problems are gone.

evidence/receipt.ts

A receipt is proof that a "verified" run happened for an exact state of the code. It binds four things: the exact source tree, a hash of the policy files, the engine version, and the scanner versions. Change any one of them and the receipt no longer matches. Creating and checking a receipt use the same hash function, so the check can never drift away from the proof.

Same input, same output

primitives/canonical.ts turns data into bytes in a fixed order and hashes them. sortKey.ts sorts in a fixed order. The clock is injected, never read from the machine. The same input always produces the same bytes and the same hash. That is why a receipt can be checked again later.

Verdict order: first, a changed policy file means "approval required", exit 2. Second, nothing to check means no verdict, exit 0. Third, a new deterministic failure means "regression", exit 1. Fourth, missing coverage or unsure evidence means "not covered", exit 3. Only after all of that: "verified", exit 0.

07

src/cli.ts and src/surfaces/

Surfaces only show or enforce the result.

A surface is a place where people or tools see the result: the command line, the browser, the AI stop hook, the pull request. Every surface reads the same Result object. No surface computes findings again on its own.

FilesSurfaceWhat the code does
cli.ts, cli-bin.ts, surfaces/cli.tsCommand lineReads the command flags, calls run(), prints text or JSON, and exits with the Result's exit code. The installed command has its own build entry file, so the build tool cannot accidentally turn it into an empty program.
surfaces/stop-hook.ts, stop-hook-runner.ts, stop-hook-bin.ts, receipt-store.tsAI stop hookConnects to Claude Code. It blocks by printing a JSON message, not by exit codes, because that is how the hook protocol works. If a valid receipt already matches the current code, the stop is allowed without a new scan. The hook blocks only once per stop, so the assistant cannot get trapped in a loop. A one-time bypass file exists for the human operator.
surfaces/vite-plugin.ts, overlay-client.tsBrowser inspectorvite-plugin.ts serves the inspector inside the running app. overlay-client.ts, the largest file in src/, draws the panel, refreshes when code changes, and can point to a finding on the page. It advises only. It can never fail a build or a process.
surfaces/pr-comment.tsPull requestRenders the Result as one pull request comment. A hidden marker lets CI update the same comment instead of adding a new one each time. Enforcement comes from the exit code in CI, not from the comment text.
surfaces/docs.ts, surfaces/docs-html.tsDocumentationdocs.ts projects a run's design-intake and transcript artifacts: an image text list, announcement examples, and keyboard paths. usabl docs prints them as JSON; usabl docs --html, rendered by docs-html.ts, writes one self-contained, accessible HTML page. It is a generator, not a gate: it always exits 0 and makes no verdict. On the page an artifact reads as verified only when it is bound to a minted receipt and its entries carry evidence; a bound artifact whose entries carry no evidence is labelled an expectation, and anything unbound is labelled an observation.
surfaces/playwright-helper.tsTest helperLets a Playwright test suite assert on an existing Result inside the tests a team already runs.
surfaces/scrub.ts, primitives/neutralize.tsOutput safetyText taken from a web page is untrusted. It can contain hidden control characters, or text that tries to give instructions to an AI. neutralize.ts removes control bytes before terminal output. scrub.ts marks page text as untrusted before it enters an AI conversation.
surfaces/self-check.tsMid-task checkA read-only status view that an AI assistant can request in the middle of a task. It reports. It never blocks.

Consistency rule: if two surfaces ever disagree, the bug is in the display code, not in the decision. Start debugging from the Result object and work outward.

08

Pick a system to maintain

The engine divides into eight systems. Each one is a job someone can own.

The sections above explain the code in the order it runs. This one groups it a different way: into eight systems with clear edges, so each engineer can take one and know exactly where it starts and stops. The edges follow how the code actually imports across files, not how the folders are named.

1. Engine core

contracts/ · run.ts · gate/ · primitives/ · index.ts

Owns the one verdict, the order the pipeline runs in, the shared data shapes every other module imports, and the small pure helpers. This is where the product's honesty guarantee lives. Own this and you own the rule that only the gate decides.

2. Scan and providers

providers/ (axe, rulepack, keyboard-walk, check-runner) · deps/

Owns how the browser is driven and how raw drafts are produced from a live page. It also computes the engine and scanner version stamps that a receipt needs. It collects evidence; it never concludes.

3. Coverage and discovery

coverage/ (planner, route-manifest, import-graph)

Owns the question of which screens a change touches. When it cannot connect a changed file to a screen, it records a gap. That gap is what makes the gate answer "not covered" instead of guessing.

4. Trust and receipts

trust/guard.ts · evidence/ · receipt-store.ts · baseline/ · floor/

Owns the tamper model, the four-part receipt (both minting and checking it), and the accepted-findings floor with its prune step. A policy change cannot approve itself, because these reads happen against the trusted copy in git.

5. Design intake and docs

intake/ · docs/ · surfaces/docs.ts · surfaces/docs-html.ts

Owns the path from written requirements to runtime checks, and from a finished run to the accessible documentation page. The three-state honesty rule for that page, verified against expectation against observation, lives here.

6. CLI and reporting

cli.ts · surfaces/cli.ts · output/ · scrub.ts · pr-comment.ts · policy-enforce.ts

Owns command routing and every read-only view of a result, for a person or for CI, plus the cleaning of untrusted page text before it leaves the tool. The usabl enforce path turns a result into a CI status without running the gate again.

7. Adoption and wiring

init/ · install/ (overlay, claude, ci, branch-rule) · doctor/ · drift/

Owns getting usabl into a repository: drafting config, wiring exactly one surface per run, and reporting what is wired or has drifted. Every step writes a reviewable draft; none of them mint a verdict.

8. Hook and overlay runtime

stop-hook*.ts · vite-plugin.ts · overlay-client.ts · playwright-helper.ts

Owns the live entry points that actually call run(): the AI stop hook, which is the headline surface, the in-browser overlay, and the Playwright test seam. All of them fail open, so a stuck hook discloses rather than blocks by accident.

Dormant lanes (built, not wired)

voicing/ · measure/fleet-insights.ts

Neither is on a production path in v0.2.0. voicing/ is a complete check that is not yet registered in deps/build.ts; measure/fleet-insights.ts is a standalone scanning harness that nothing else imports. When they are switched on, voicing folds into Scan and providers, because it is already a valid provider, and measure folds into CLI and reporting. They are flagged here so nobody assumes they run today.

One caution for every maintainer: three names look alike but mean different things. The word "verified" in install/branch-rule.ts is the name of a required CI check, not a gate verdict. CoverageGap uses "not-covered" with a hyphen for an unchecked screen, while the gate verdict "not_covered" uses an underscore. output/conformance.ts echoes the verdict for display and sets a "blocked" flag, but it never mints one. When in doubt, the verdict comes from one place only: gate/index.ts.

09

The rest of src/

The supporting code, in one map.

primitives/

Small shared helpers with no opinions: hashing, sorting, file pattern matching, name shortening, identity keys, and terminal output cleaning. Nothing here reads files or makes decisions.

docs/

Generators that turn a Result into documents: image text lists, announcement examples, and keyboard path descriptions. One shared helper checks the link between a document and its evidence, so no generator can invent its own weaker check. The usabl docs command projects these as JSON, and surfaces/docs-html.ts renders them as an accessible HTML page (see Surfaces).

output/

Text views of a finished Result: the terminal summary and a conformance view. The conformance view refuses to merge all findings into one single score, because one score hides information.

measure/fleet-insights.ts

A measurement tool for scanning real applications. It counts drafts, keyboard stops, and gaps. It never calls the gate. It never produces a verdict or a receipt.

integration-smoke.ts

A manual test entry that uses a real browser. An environment variable guard stops it from reporting success when the browser is not available.

index.ts

The public entry of the library. Its whole header comment is one sentence, and that sentence is the architecture: callers display a Result; they do not make a verdict.

Suggested reading order for a new contributor: read contracts/index.ts first, for the data shapes. Then run.ts, for the order of steps. Then gate/index.ts, for the decision. Then coverage/planner.ts and providers/check-runner.ts, for the evidence. After that, read the surface you plan to change.
