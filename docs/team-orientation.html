Prove the change before we call it done.

usabl checks the user interface affected by a code change. It reports what passed, what regressed, what it could not cover, and when a human must decide.

The AI can suggest a fix. It does not get to grade its own work.

02

The result model

The result states what usabl checked.

○ Idle state: no relevant interface changed, so no check was needed and no verdict was issued.

✓ Verified

The required checks found no new barrier in the screens they covered.

× Regression

A required check found a new accessibility barrier.

? Not covered

One or more required screens or checks could not run.

! Approval required

Trusted policy or gate code changed. A human owner must review it.

Why this matters: a tool that silently skips a screen can look green while knowing less. usabl reports missing coverage as work the team must resolve.

03

How it works

Many checks. One decision. One result.

The command line, app overlay, AI check, and pull request all show the same decision.

Providers

Collect evidence

  • axe WCAG checks
  • PatternFly rules
  • Keyboard walk
→
Gate

Decide once

Checks coverage and policy, then compares new barriers with the accepted baseline.

→
Result

Carry one result

Verdict, findings, coverage, evidence, exit code, and receipt.

→
Surfaces

Show or enforce

  • Local command
  • AI completion check
  • In-app overlay
  • PR comment and CI

The invariant: providers return evidence drafts. The gate is the only part of usabl allowed to mint a verdict or verified receipt.

04

The hero loop

One change. One proof loop.

The fixture contains a real PatternFly modal focus regression. Experience it, see usabl report it, repair the behavior, and verify the exact new code state.

Feel the defect

Open cluster details. Press Escape. Focus does not return to the trigger.

Run usabl

From usabl-app, run npx usabl check.

Read the result

Expect regression, rule pf-modal-focus-return, and exit code 1.

Repair focus

Restore triggerEl.focus() when the modal closes.

Run it again

The same engine checks the changed source and affected screen.

Verify proof

Expect verified and a receipt bound to that source tree.

usabl-app $ npx usabl check
verdict: REGRESSION
rule: pf-modal-focus-return
exit: 1

usabl-app $ npx usabl check
verdict: VERIFIED
receipt: bound to source tree
exit: 0
Before

Escape closes the dialog. Keyboard focus is lost.

→
After

Focus returns to “View cluster details.”

Exact setup commands for developers

Use Node.js 22. Both private repositories must be cloned as siblings.

git clone https://github.com/usabl-dev/usabl.git
git clone https://github.com/usabl-dev/usabl-app.git
cd usabl && npm install && npm run build
cd ../usabl-app && npm install && npm run dev

Open http://127.0.0.1:5173/clusters. The ?variant=fixed option is an automated test oracle. Fix the code when testing the team ratchet.

Your first working session

Use the first hour well.

  1. Join the teamGet the team channel, orientation, demo, and issue tracker links.
  2. Read the result modelFinish sections 01 through 05.
  3. See the proof loopWatch it live, guide it, or run it yourself.
  4. Choose a laneName the result, surface, or outcome you will own.
  5. Record evidenceFile an issue, propose a pull request, or record a test observation.

Outcome: you can explain the result model, point to the proof loop, and name your next contribution.

Pull request hygiene for contributors

Before opening

  • Cut a focused branch from current main.
  • Write a failing test first for behavior changes.
  • Use Conventional Commits.
  • Run pre-commit run --all-files and npm run check.
  • Do not skip hooks or add AI co-author trailers.

Before merge

  • Explain the pull request in one sentence.
  • Complete the summary, test plan, and AI note.
  • Get independent engineering and security review.
  • Let the founder make the merge decision.
  • Use squash merge only.
08

Three weeks to the contest

Finish around proof, not feature count.

Each week ends with something the team can run, inspect, and repeat. Replace role labels with names as work is claimed.

WEEK 1

Harden and onboard

  • Merge package hardening after review.
  • Get every teammate through orientation.
  • Run the loop from a clean clone.
  • Own every onboarding issue.

Exit: another teammate can guide the loop without the builder.

WEEK 2

Test and sharpen

  • Test keyboard and screen-reader behavior.
  • Resolve high-impact false results and gaps.
  • Make all four surfaces agree.
  • Freeze the scenario and claim set.

Exit: the proof survives skeptical team testing.

WEEK 3

Rehearse and prove

  • Practice the live demo to time.
  • Capture backup evidence.
  • Rehearse failure recovery and handoffs.
  • Freeze candidates and verify receipts.

Exit: two people can deliver and recover the demo.

Who decides what

  • Founder: product, UX, scope, and merge.
  • CTO: architecture changes and the technical quality bar.
  • Implementer: test-first code and focused commits.
  • Reviewers: engineering quality and security risk.

What remains at v0.1.0

  • Harden the installed package path.
  • Expand testing beyond the original builder.
  • Turn observations into owned pull requests.
  • Polish the demo and backup path.
  • Keep security approval visible before merge.
09

Claim boundary

Say exactly what v0.1.0 proves.

What we can claim

  • usabl evaluates affected user interface surfaces.
  • One gate calculates the result used by every surface.
  • Verified evidence is tied to exact code, policy, and runner.
  • Missing coverage becomes not_covered.
  • The demo proves a real focus regression and repair.

What we cannot claim

  • We do not guarantee accessibility outside executed coverage.
  • We do not replace disabled users or accessibility experts.
  • We do not claim legal compliance.
  • Preview and model judgment do not mint receipts.
  • v0.1.0 is a private team preview.

Feedback that helps

Name the surface, result seen, expected result, exact steps, and whether the output was honest or confusing.

Open the usabl feedback form or bring the observation to the team channel.
