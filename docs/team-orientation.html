02

The result model

The result states what usabl checked.

○ Idle state: no relevant interface changed, so no check was needed and no verdict was issued.

✓ Verified

The required checks found no new barrier in the screens they covered.

× Regression

A required check found a new accessibility barrier.

? Not covered

One or more required screens or checks could not run.

! Approval required

Trusted policy or gate code changed. A human owner must review it.

Why this matters: a tool that silently skips a screen can look green while knowing less. usabl reports missing coverage as work the team must resolve.

03

How it works

Many checks. One decision. One result.

The command line, app overlay, AI check, and pull request all show the same accessibility decision. Read the full system guide to see how coverage, evidence, the gate, receipts, and surfaces connect.

Providers

Collect evidence

  • axe WCAG checks
  • PatternFly rules
  • Keyboard walk
→
Gate

Decide once

Checks coverage and policy, then compares new barriers with the accepted baseline.

→
Result

Carry one result

Verdict, findings, coverage, evidence, exit code, and receipt.

→
Surfaces

Show or enforce

  • Local command
  • AI completion check
  • In-app overlay
  • PR comment and CI

The invariant: providers return evidence drafts. The gate is the only part of usabl allowed to mint a verdict or verified receipt.

Pull request hygiene for contributors

Before opening

  • Cut a focused branch from current main.
  • Write a failing test first for behavior changes.
  • Use Conventional Commits.
  • Run pre-commit run --all-files and npm run check.
  • Do not skip hooks or add AI co-author trailers.

Before merge

  • Explain the pull request in one sentence.
  • Complete the summary, test plan, and AI note.
  • Get independent engineering and security review.
  • Resolve required reviews and checks.
  • Use squash merge only.
08

Team handoff

usabl v0.2.0 is ready for the team to pick up.

Onboard, run the accessibility proof from a clean clone, exercise the four surfaces, choose a contribution lane, and keep the evidence current. This is what a teammate does now, with no date to wait on.

STEP 1

Onboard

  • Read this orientation and How usabl works.
  • Learn the result model, the four surfaces, and the claim boundary.

Ready when: you can explain what usabl proves and does not prove.

STEP 2

Run the proof

  • Clone usabl and follow the accessibility proof-loop guide.
  • Exercise all four surfaces: CLI, overlay, Stop hook, and the pull request check.
  • Watch one regression and its repair carry the same result.

Ready when: the loop runs end to end from a clean clone.

STEP 3

Contribute and keep evidence current

  • Pick a lane above and make one focused change.
  • Re-run usabl baseline and usabl floor prune so the evidence floor stays honest.
  • Keep receipts and coverage current as the app changes.

Ready when: your lane has a first contribution in review.

Adoption commands

Six commands wire and maintain usabl from a clone. Each one writes a draft, reads state, or reports drift, and none of them mints a verdict. Only the gate does that.

CommandWhat it does
usabl initDrafts coverage and policy from the application tree. It does not run the gate and does not write waivers or evidence.
usabl baselineRuns a full user interface scan and drafts .usabl-evidence.json from deterministic findings as a reviewable working-tree diff.
usabl floor pruneAfter a full scan, removes paid-down identities from .usabl-evidence.json so a reintroduced barrier gates as new instead of staying carried.
usabl drift routesReports drift between the route manifest and the application router. It reads only and mints no verdict.
usabl installWrites one adoption draft and enables nothing on its own. Choose exactly one target: --overlay, --claude, --ci, or the read-only --branch-rule.
usabl doctorRead-only self-check that reports each surface as wired, missing, drifted, or unknown, and mints no verdict.

After you onboard: the human-tasks.md catalogue in the usabl-plans repo lists the work that needs a person, including a clean-clone onboarding proof, an assistive-technology review, and a two-operator guarded-change rehearsal. Like the rest of usabl-plans, it stays with the plans and does not ship in the product package.

09

Claim boundary

Say exactly what v0.2.0 proves.

What we can claim

  • usabl evaluates affected user interface surfaces.
  • One gate calculates the result used by every surface.
  • The Stop hook can block incomplete accessibility work.
  • Verified evidence is tied to exact code, policy, runner, and scanner stack.
  • Missing coverage becomes not_covered.
  • The demo proves multiple accessibility barriers and their repair.

What we cannot claim

  • We do not guarantee accessibility outside executed coverage.
  • We do not replace disabled users or accessibility experts.
  • We do not claim legal compliance.
  • Preview and model judgment do not mint receipts.
  • Fleet Insights is measurement, not a verdict.
  • v0.2.0 is a private team preview.

Feedback that helps

Name the surface, result seen, expected result, exact steps, and whether the output was honest or confusing.

Open the usabl feedback form or bring the observation to the team channel.
