Background

The Verification Gap

Code generation and AI assistants accelerate UI development, but accessibility verification remains an out-of-band, manual process.

A page scanner produces an issue list for a page. On its own it does not map a git diff to affected routes, re-check a fix, or block a merge.

System Concept

Automated Accessibility Proof

The gap is between what gets written and what ships to a user who depends on accessibility. usabl closes it by evaluating UI changes automatically, as part of the existing merge workflow, before code reaches production.

Targeted Execution Maps changed files to specific application routes and runs checks only on affected screens.
Strict Enforcement Compares results against a known baseline. Blocks new regressions while allowing existing technical debt to be managed over time.

Targeting

How usabl Knows What to Check

usabl does not re-scan the whole app on every change. It reads the git diff and works out which screens each changed file can actually affect, then checks only those. A file it cannot trace to a screen is reported as not covered, never quietly passed.

Architecture

Separation of Evaluation and Enforcement

A scanner that both finds issues and decides outcomes is hard to audit and easy to game. usabl separates these responsibilities: providers only report findings, and a single Gate makes every pass-or-fail decision against committed policy.

Providers Modules like axe-core or custom scripts that inspect the page and emit findings (Draft[]). Providers never decide the final outcome.
The Gate The central authority. It evaluates all drafts against the baseline and waivers, then issues a single final verdict for the run.

Gate Outputs

Four Deterministic Verdicts

A list of issues is not an answer. In a CI pipeline or an AI-assisted workflow, the system needs one unambiguous decision: can this change ship? When the Gate checks something, it produces exactly one of four verdicts. Each names a specific state with a specific required response.

verifiedexit 0

No new accessibility barriers were found on the touched surfaces, and coverage was complete.

regressionexit 1

A new machine-checkable barrier was introduced. The build or commit is blocked.

not coveredexit 3

A changed file could not be mapped to a scannable page, so the check could not vouch for it. usabl fails closed rather than passing silently.

approval requiredexit 2

The change touches a baseline, waiver, or policy file, so it needs an explicit code-owner review before it can pass.

Two outcomes carry no verdict. An idle run, where no changed file maps to a covered screen, exits 0 with no receipt. A run that could not produce a verdict (a crash, an unreadable configuration file, or no affected screen rendering) exits 4 and prints the reason. Neither is a pass. usabl only claims verified when it checked something.

Evaluation

Multi-Layered Checks

No single scanner catches everything. DOM validation misses keyboard behavior. Focus testing misses ARIA attributes. Neither understands design system composition contracts. Three layers each cover a different part of the machine-checkable surface. Together they do not cover all of WCAG 2.2 AA.

axe-core Executes the standard axe-core 4.13 ruleset for baseline DOM, ARIA, and contrast validation.
Keyboard Walk Dynamically tabs through the page, reading the accessibility tree to verify focus order and accessible names.
PatternFly Rules Component-specific composition rules (e.g., modal focus return, menu state) that generic scanners miss.

Deep Dive

Keyboard Walk Provider

Static analysis cannot verify interactive focus behavior. The Keyboard Walk provider physically tabs through the document and inspects the accessibility tree at each stop.

Unnamed Interactive Elements Flags any element in the tab order that exposes an interactive role (button, link, etc.) but lacks a computed accessible name.
Unconfirmed Focus Flags tab stops where the accessibility tree node cannot be resolved, so an unconfirmed stop is reported instead of passing in silence.

Deep Dive

PatternFly Composition Rules

Generic scanners check DOM elements in isolation. They cannot verify design system behavioral contracts: a modal must return focus to its trigger, a menu must expose its expanded state, table row actions must have unique names. These are real accessibility failures users encounter, but they require understanding how the component is supposed to behave, not just what its markup looks like.

Static rules inspect the DOM directly. Interaction probes exercise real component behavior in a live browser.

RuleValidation Target
pf-icon-button-nameEnsures icon-only controls have accessible names.
pf-kebab-expanded-stateVerifies menu toggles expose expanded/haspopup states.
pf-row-action-name-uniquePrevents table row actions from sharing identical names (e.g., multiple "Delete" buttons).
pf-table-header-assocEnsures data cells are programmatically bound to headers.
pf-toast-live-regionVerifies alerts are contained within active live regions.
pf-focus-into-dialogEnsures focus moves into a dialog upon activation.
pf-modal-focus-returnVerifies focus returns to the trigger element when a modal is closed.
pf-toolbar-labeled-when-repeatedRequires a distinguishing label when a toolbar appears more than once, so each is identifiable.

Deep Dive

Design Intake (Optional)

Some accessibility requirements cannot be inferred by scanning a rendered page: an approved label, a specific spoken announcement, a promised image description. Design intake lets a team author those expectations as reviewed data, and the engine checks them the same way it checks everything else.

Content Assert that a specific element's accessible name matches approved text, is non-empty, or is intentionally decorative with no exposed name.
Flow Assert that after a sequence of interactions, tab, click, or key presses, a specific announcement reaches assistive technology through focus or a live region.
Doc Require a generated artifact to exist and stay current: an alt-text manifest, announcement snippets, or keyboard paths, projected read-only by usabl docs.

In CI the bundle is read from the trusted base reference, so a pull request cannot rewrite the requirements it is graded against. A malformed bundle yields approval required, never a silent pass.

Integrations

Consistent Execution Across Environments

If the check only runs in CI, inaccessible code gets written and caught minutes later in a failed build. If it only runs in the AI assistant, a human path skips it. The same engine runs behind every surface so feedback arrives where the change is made. The Stop hook and CI enforce; the dev-server overlay is advisory; the Playwright helper is a page-level check.

Workflow

Managing Legacy Codebases

usabl is designed for brownfield adoption. It does not block builds for pre-existing issues.

The Floor usabl baseline runs a full scan and records the deterministic findings it observed into a committed evidence file. These known issues are tracked but do not fail the build. The baseline refuses to record a floor from a run that did not see every screen, unless asked for a labeled partial floor.
The Ratchet The gate only blocks on new deterministic failures. As legacy issues are fixed, the floor is pruned, preventing regressions.
Waivers Exceptions can be granted via a waiver ledger, requiring an owner, reason, and strict expiration date.

In Practice

A Change That Gets Blocked

Here is one change moving through the gate, end to end.

  1. A developer tidies a shared IconButton and drops its label.
  2. usabl follows the import graph: that component is used on three screens, so all three are checked.
  3. axe-core, the keyboard walk, and the PatternFly rules run in a real browser. One finds a new barrier: an icon-only button with no name.
  4. The verdict is regression, so the pull request is blocked with this comment.
## usabl report: REGRESSION

Receipt: none. This run was not verified.

Deterministic:  1 new · 0 carried · 0 waived
Coverage:       3 screens checked · 0 not covered
Blocked:        yes

New barriers
- [serious] `settings` - `pf/pf-icon-button-name`
  A screen reader announces only "button", so the control's purpose is lost.
  why: the icon-only button has no accessible name
  fix: add an accessible name, e.g. aria-label="Delete row"

CI / GitHub

The Pull Request Gate Is Three Jobs

The gate is three GitHub jobs. Only one runs the pull request's own code, and only one decides the merge. That split is what makes the verdict trustworthy.

gate-commentBuilds and runs the head code in a real browser, scans, posts the comment, and uploads the Result. Fenced to pull_request events, where fork code is denied secrets.
usabl-policyNever runs head code. Checks out the trusted base, reads the head as git objects only, and decides policy from CODEOWNERS and the trusted ref. Publishes the accessibility verdict from the Result.
usabl-requiredThe required status check. It is the only job that sees both the accessibility verdict and the policy verdict, and it decides merge or block.

CI / GitHub

A Pull Request Cannot Grade Itself

Three properties keep a pull request from passing itself, and keep untrusted code away from secrets.

Trusted base refPolicy is read from origin/main, not from the pull request head. A change cannot rewrite the rules, the guarded paths, or CODEOWNERS in the same diff and pass under its own new rules.
Head-code fenceOnly gate-comment runs head code, and only on pull_request events, where a fork's code is denied repository secrets. Review events carry secrets, so those jobs never check out or execute the head; they read it as git objects.
Fail closedNo Result is a fail. A verdict that is not exactly pass is a fail. A skipped or cancelled job blocks. The verdict starts at fail and only a clean run moves it, so nothing missing is ever read as clean.

CI / GitHub

The Check to Require, and Review Re-Runs

Require usabl-required, not the other two. gate-comment cannot run on a review event, and usabl-policy passing says nothing about accessibility. Only usabl-required sees both verdicts.

always() is load-bearingGitHub counts a skipped required job as satisfied. An aggregate that could be skipped would be an open gate, so this job always runs and always decides.
Approvals flip the gate without re-scanningA CODEOWNERS approval fires a review event. The scan does not re-run. usabl-policy finds the completed scan for that exact commit and reads its Result artifact, so an approval flips the gate deterministically and no head code runs on the event that carries secrets.
One verdict pathThe accessibility verdict travels as data read from the Result, never inferred from a job's pass or fail. On a review re-run, where the scan job is skipped, that artifact is the only accessibility authority that exists.

Integrations

Runs Inside Your Playwright Suite

Teams already drive their app through real user flows in end-to-end tests. usabl reuses those flows instead of asking for new ones: navigate and interact exactly as you do today, then hand the live page to one function. It runs the same axe-core, PatternFly, and keyboard-walk providers on the exact interactive state your test reached, and returns a page-level result you assert on.

// a11y.spec.ts: assert on the flow you already test
import { test, expect } from '@playwright/test';
import { checkPage } from 'usabl/playwright';

test('cluster list stays accessible', async ({ page }) => {
  await page.goto('/clusters');
  await page.getByRole('button', { name: 'Filter' }).click();

  // same axe + PatternFly + keyboard-walk providers as the gate
  const result = await checkPage(page);

  expect(result.failures).toEqual([]);       // no deterministic barriers on this page
  expect(result.verdict).toBe('verified');   // no failures and no provider gaps on this page
});
Same providers, deeper reachAssertions run on post-interaction states, such as open menus, dialogs, and wizards, that a route-level scan never reaches.
One importcheckPage(page) from usabl/playwright adopts the page without closing it, then returns the findings and a page-level verdict.
Not the gated commandThis check has no evidence floor and no waivers, so a barrier the gate has already accepted still reads as a regression here. Its verdict can differ from usabl check. A check that could not be confirmed is not_covered, never a quiet green.

usabl is not yet published to a package registry; build it from source. The page from the @playwright/test fixture is passed straight through.

Integrations

Stops an AI Agent From Declaring Done

When an AI coding agent finishes a task, a stop hook runs the same gate on the screens it touched. If the gate is not verified, the agent cannot mark the task complete. It gets the verdict, the reason, and the fix, and has to address them first. If the hook itself fails, it exits 0 and reports NOT verified instead of blocking by accident.

Same engineThe hook runs the same axe-core, keyboard-walk, and PatternFly engine as CI, against the local evidence floor and waivers. CI reads those files from the trusted base branch, so the two can differ when the local files differ from the base.
Closes the agent loopWithout it, an agent can ship an inaccessible change between human reviews. The hook puts the check at the moment of completion, where it is cheapest to fix.
Blocks on new onlyLike CI, it blocks new deterministic barriers, not the pre-existing floor, so it does not stall an agent on legacy debt it did not create. Missing coverage and a changed policy file also block.

Integrations

Findings on the Live App, While You Build

A Vite plugin adds an advisory inspector to the running application. It projects the Result the gate produced for the local working tree and never mints a verdict. It is read only and never gates.

Locate on the pageEach finding highlights the affected element on the live app, so a barrier is a place you can see rather than a selector to decode.
Jump to sourceWhen the app is built with the usabl dev transform, a finding links to the file and line that rendered the element.
Advisory, and whyThe inspector runs inside the tested page's own JavaScript, so the page can interfere with what it shows. Page text is rendered as text, never as HTML. The terminal command, CI, and the stop hook decide; the overlay only shows.

Extending the Engine

usabl for Documentation

usabl checks the application for new machine-checkable accessibility barriers. The same engine checks product documentation pages listed in a manifest, so the user guides and install guides that ship with the product are held to the same rules, automatically, each time they change.

The Gap

Documentation Is the Largest Unchecked Surface

Teams that test their application for accessibility often do not test the documentation that ships with it.

Customer Impact Documentation is how customers actually learn to use a product. A person who relies on a screen reader may be able to operate the app, but if the install guide has images with no descriptions or headings in the wrong order, the product has still failed that customer.
Compliance Impact The same standard that applies to the app, WCAG 2.2 AA, applies to the docs. Without a check in the pipeline, nothing checks the docs against it.

What It Does

Checks the Real, Published Pages

It checks the rendered documentation pages listed in the manifest, the thing a customer sees, each time their sources change, and flags machine-checkable problems before they reach customers.

Findings in the Writer's Source When it finds a problem, it says what is wrong and how to fix it, and maps the finding back to the writer's own source file and, where it can resolve it, the AsciiDoc construct.
Targeted Re-Checks It only re-checks the pages whose sources changed, so it stays fast, and it blocks a new machine-checkable barrier on the pages it scanned.

Why It Matters

Four Reasons This Closes a Real Gap

Reduces Compliance Risk Checks the docs against the WCAG 2.2 AA rules the engine can check by machine, at a time when the European Accessibility Act and Section 508 are raising the stakes. It runs on each change instead of once a year. It does not claim compliance.
Reaches More Customers Documentation is a large part of the product experience. Removing machine-checkable barriers before they ship helps customers who rely on assistive technology.
Lowers Cost Adds an automatic check to the pipeline the docs team already uses, so fewer problems reach a manual audit. It does not replace manual audits or testing with disabled users.
Catches Problems Early Issues are caught at the moment of the change, before publishing, when they are cheap to fix, rather than after a customer complaint or an external audit finding.

Why Now

One Engine, Two Surfaces

The obligation already exists. Design systems cover the page frame, the navigation and theme. The authored content, the words and images a writer produces, goes unchecked unless something checks it. This closes that specific, named gap by reusing the engine already used for the application, rather than building or buying a separate product.

Security

Protecting the Verdict

Two things could make a real barrier disappear: someone edits the policy to silence a failure, or a scanned page feeds hostile text back into the pipeline. A developer under deadline pressure, or an AI assistant optimizing for task completion, has motive to do the first. usabl has a control for each.

Trusted References In CI, verdicts are computed against the baseline and configuration from the target branch (for example main), not the pull request's working tree. A pull request cannot weaken its own policy to make itself pass. Locally, a changed policy file is detected and turns the verdict into approval_required.
Codeowner Enforcement Any change to a baseline, waiver, config, or route mapping turns the verdict into approval_required, so a human owner has to review it.
Page Text Marked as Data Text read from a scanned page, such as a label or heading, has control sequences stripped and credential-shaped values redacted. Where it reaches an AI assistant it sits inside a labeled frame that names it as data rather than instructions, and the frame delimiters are removed from page text so a page cannot close its own frame.

Evidence

A Re-Checkable Receipt

"We checked it" is not evidence. A compliance team, an auditor, or a future developer needs to confirm for themselves that a specific change was tested before it shipped.

When a run is verified, usabl writes a small receipt that records what the result depended on: a hash of the source tree, a hash of the committed policy, the engine version, and the exact scanner versions. Re-verification recomputes those values and compares them. It does not re-scan. If any value changed, the receipt no longer holds.

Ways to Use It

Every Surface, and What It Enforces

The same engine backs every way you use usabl. Most surfaces block a new barrier the moment it appears; the dev-server overlay is advisory; design intake feeds the engine your own rules; and changing policy files needs a human sign-off.

AI assistant Blocks The Stop hook will not let Claude Code finish a turn while the gate is red. Run /usabl-check at any point to scan work in progress.
CI / pull request Blocks A required status check gates merge and posts a findings comment on the pull request. Editing policy files adds the approval gate below.
Browser overlay Advisory The Vite dev-server plugin shows the gate's findings on your running app. It runs inside the page's own JavaScript, so it is read-only and never blocks a build or a commit.
Playwright Blocks checkPage() runs the providers on one live page inside your existing E2E suite, and your assertion fails the test. It has no evidence floor and no waivers, so it can differ from usabl check.
Design intake Input Author accessibility requirements as guarded YAML. Content and flow rules become deterministic checks in every run, and generate alt-text, keyboard-path, and announcement docs.
Product docs Blocks Point the same engine at your built AsciiDoc docs at WCAG 2.2 AA. Findings map back to the source .adoc file.

Approval Policy and config files (the config, the evidence floor, the waiver ledger, the route manifest, and any guarded paths) are protected. A pull request that changes them stays approval required until a CODEOWNERS reviewer other than the author approves that exact commit on GitHub. usabl bypass affects only the next local Stop hook run; nothing local bypasses the pull request gate.

Summary

Continuous Accessibility Verification

usabl moves accessibility checking into the everyday workflow, the CLI, CI, and AI assistants, instead of a separate audit that happens later.

It records existing issues as a baseline, blocks only new ones, and points the same engine at both the application and its documentation. Teams can change the UI, and the docs, knowing that no new machine-checkable barrier reached the screens and pages it checked, and that anything it could not check was reported.
