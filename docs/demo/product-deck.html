Technical Overview

usabl

An accessibility proof engine for UI development. Integrates deterministic checks into the developer workflow across the CLI, CI, and AI assistants.

Background

The Verification Gap

Code generation and AI assistants accelerate UI development, but accessibility verification remains an out-of-band, manual process.

Standard scanners produce issue lists for static pages, but they do not map git diffs to affected routes, verify fixes automatically, or prevent inaccessible code from being merged.

System Concept

Automated Accessibility Proof

The gap is between what gets written and what ships to a user who depends on accessibility. usabl closes it by evaluating UI changes automatically, as part of the existing merge workflow, before code reaches production.

Targeted Execution Maps changed files to specific application routes and runs checks only on affected screens.
Strict Enforcement Compares results against a known baseline. Blocks new regressions while allowing existing technical debt to be managed over time.

Targeting

How usabl Knows What to Check

usabl does not re-scan the whole app on every change. It reads the git diff and works out which screens each changed file can actually affect, then checks only those. A file it cannot trace to a screen is reported as not covered, never quietly passed.

Architecture

Separation of Evaluation and Enforcement

A scanner that both finds issues and decides outcomes is hard to audit and easy to game. usabl separates these responsibilities: providers only report findings, and a single Gate makes every pass-or-fail decision against committed policy.

Providers Modules like axe-core or custom scripts that inspect the page and emit findings (Draft[]). Providers never decide the final outcome.
The Gate The central authority. It evaluates all drafts against the baseline and waivers, then issues a single final verdict for the run.

Gate Outputs

Four Deterministic Verdicts

A list of issues is not an answer. In a CI pipeline or an AI-assisted workflow, the system needs one unambiguous decision: can this change ship? The Gate produces exactly one of four verdicts for every run. Each names a specific state with a specific required response. There is no ambiguous middle ground.

verifiedexit 0

No new accessibility barriers were found on the touched surfaces, and coverage was complete.

regressionexit 1

A new machine-checkable barrier was introduced. The build or commit is blocked.

not coveredexit 3

A changed file could not be mapped to a scannable page, so the check could not vouch for it. usabl fails closed rather than passing silently.

approval requiredexit 2

The change touches a baseline, waiver, or policy file, so it needs an explicit code-owner review before it can pass.

An idle run with nothing to check exits 0 without minting a receipt, and that is kept distinct from verified: usabl only claims verified when it actually checked something.

Evaluation

Multi-Layered Checks

No single scanner catches everything. DOM validation misses keyboard behavior. Focus testing misses ARIA attributes. Neither understands design system composition contracts. Three complementary layers cover the real accessibility surface.

axe-core Executes the standard axe-core 4.13 ruleset for baseline DOM, ARIA, and contrast validation.
Keyboard Walk Dynamically tabs through the page, reading the accessibility tree to verify focus order and accessible names.
PatternFly Rules Component-specific composition rules (e.g., modal focus return, menu state) that generic scanners miss.

Deep Dive

Keyboard Walk Provider

Static analysis cannot verify interactive focus behavior. The Keyboard Walk provider physically tabs through the document and inspects the accessibility tree at each stop.

Unnamed Interactive Elements Flags any element in the tab order that exposes an interactive role (button, link, etc.) but lacks a computed accessible name.
Unconfirmed Focus Flags tab stops where the accessibility tree node cannot be resolved, preventing silent failures on focus traps.

Deep Dive

PatternFly Composition Rules

Generic scanners check DOM elements in isolation. They cannot verify design system behavioral contracts: a modal must return focus to its trigger, a menu must expose its expanded state, table row actions must have unique names. These are real accessibility failures users encounter, but they require understanding how the component is supposed to behave, not just what its markup looks like.

Static rules inspect the DOM directly. Interaction probes exercise real component behavior in a live browser.

RuleValidation Target
pf-icon-button-nameEnsures icon-only controls have accessible names.
pf-kebab-expanded-stateVerifies menu toggles expose expanded/haspopup states.
pf-row-action-name-uniquePrevents table row actions from sharing identical names (e.g., multiple "Delete" buttons).
pf-table-header-assocEnsures data cells are programmatically bound to headers.
pf-toast-live-regionVerifies alerts are contained within active live regions.
pf-focus-into-dialogEnsures focus moves into a dialog upon activation.
pf-modal-focus-returnVerifies focus returns to the trigger element when a modal is closed.
pf-toolbar-labeled-when-repeatedRequires a distinguishing label when a toolbar appears more than once, so each is identifiable.

Deep Dive

Design Intake (Optional)

Some requirements cannot be inferred by scanning a rendered page. Design intake lets a team author those expectations directly, as data, and the engine checks them the same way it checks everything else.

Content Assertions Assert that a specific element's accessible name matches approved text, is non-empty, or is intentionally decorative with no exposed name.
Flow Assertions Assert that after a sequence of interactions, tab, click, or key presses, a specific announcement reaches assistive technology through focus or a live region.

Authored requirements become additional Provider modules. They report findings the same way axe-core or the Keyboard Walk do, and they still pass through the Gate. They do not bypass it.

Integrations

Consistent Execution Across Environments

If the check only runs in CI, inaccessible code gets written and caught minutes later in a failed build. If it only runs in the AI assistant, someone can bypass it. The same engine runs across every surface so feedback is immediate wherever the change is made, and no path skips the check.

CLIusabl check runs the gate locally.
Assistant HookBlocks AI agents from marking tasks complete if regressions are introduced.
Dev ServerVite plugin overlays findings directly on the local application.
CI / GitHubRequired status check and automated PR comments detailing findings.
PlaywrightIntegrates into existing E2E test suites.
DocsGenerates JSON/HTML evidence reports bound to specific commits.

Workflow

Managing Legacy Codebases

usabl is designed for brownfield adoption. It does not block builds for pre-existing issues.

The Floor usabl baseline records all current violations into a committed evidence file. These known issues are tracked but do not fail the build.
The Ratchet The gate only blocks on new deterministic failures. As legacy issues are fixed, the floor is pruned, preventing regressions.
Waivers Exceptions can be granted via a waiver ledger, requiring an owner, reason, and strict expiration date.

In Practice

A Change That Gets Blocked

Here is one change moving through the gate, end to end.

  1. A developer tidies a shared IconButton and drops its label.
  2. usabl follows the import graph: that component is used on three screens, so all three are checked.
  3. axe-core, the keyboard walk, and the PatternFly rules run in a real browser. One finds a new barrier: an icon-only button with no name.
  4. The verdict is regression, so the pull request is blocked with this comment.
## usabl report: REGRESSION

Receipt: none. This run was not verified.

Deterministic:  1 new · 0 carried · 0 waived
Coverage:       3 screens checked · 0 not covered
Blocked:        yes

New barriers
- [serious] `settings` - `pf/pf-icon-button-name`
  A screen reader announces only "button", so the control's purpose is lost.
  why: the icon-only button has no accessible name
  fix: add an accessible name, e.g. aria-label="Delete row"

Illustrative. A real comment also lists carried, waived, and advisory findings, plus any coverage gaps.

Extending the Engine

usabl for Documentation

usabl already proves that the application meets accessibility standards. The same engine now checks product documentation, so the user guides and install guides that ship with the product are checked and enforced to the same bar, automatically, every time they change.

The Gap

Documentation Is the Largest Unchecked Surface

Companies test their applications for accessibility but almost never test the documentation that ships with them.

Customer Impact Documentation is how customers actually learn to use a product. A person who relies on a screen reader may be able to operate the app, but if the install guide has images with no descriptions or headings in the wrong order, the product has still failed that customer.
Compliance Impact The same standard that applies to the app, WCAG 2.2 AA, applies to the docs. Today nothing checks the docs against it automatically.

What It Does

Checks the Real, Published Pages

It checks the actual rendered documentation pages, the real thing a customer sees, every time the docs change, and flags problems before they reach customers.

Findings in the Writer's Source When it finds a problem, it points to exactly what is wrong and how to fix it, in the writer's own source, not as a technical error code.
Targeted Re-Checks It only re-checks the pages that changed, so it stays fast, and it will not let a change introduce a new accessibility problem.

Why It Matters

Four Reasons This Closes a Real Gap

Reduces Compliance Risk Closes a gap in meeting WCAG 2.2 AA, the bar already committed to, at a time when the European Accessibility Act and Section 508 are raising the stakes. Continuous, not a once-a-year audit that is out of date the next day.
Reaches More Customers Documentation is half the product experience. This makes it usable by everyone, including customers with disabilities.
Lowers Cost Replaces expensive periodic manual audits with a check that runs automatically in the pipeline the docs team already uses.
Catches Problems Early Issues are caught at the moment of the change, before publishing, when they are cheap to fix, rather than after a customer complaint or an external audit finding.

Why Adoption Is Easy

No New Tool, No Wall of Findings

This is the same engine, and the same baseline-and-ratchet model already covered, pointed at a second surface.

No New Tool for Writers It is the same check the application team already uses, pointed at the docs. Nothing new to learn.
Baseline First Existing issues are recorded as a known baseline on day one. Only new problems block. Quality improves steadily instead of every change stalling behind a wall of pre-existing findings.
Fits the Existing Pipeline For our documentation, that is the standard AsciiDoc and Pantheon toolchain. There is nothing new to stand up.
Results Where Writers Already Look Findings show up in a pull request the same way a failing test does, so problems are visible and get fixed before anything ships.

Why Now

One Engine, Two Surfaces

The obligation already exists, but no tool checks documentation content automatically today. Design systems cover the page frame, the navigation and theme. The authored content, the words and images a writer produces, goes unchecked. This closes that specific, named gap by reusing an engine already trusted for the application, rather than building or buying a separate product.

Security

Protecting the Verdict

Two things could make a real barrier disappear: someone edits the policy to silence a failure, or a scanned page feeds hostile text back into the pipeline. A developer under deadline pressure, or an AI assistant optimizing for task completion, has motive to do the first. usabl guards against both.

Trusted References Verdicts are computed against the baseline and configuration from the target branch (e.g., main), not the working tree. A pull request cannot weaken its own policy to make itself pass.
Codeowner Enforcement Any change to a baseline, waiver, or route mapping automatically triggers an approval_required verdict, so a human owner has to review it.
Neutralized Content Any text read from a scanned page, such as a label or heading, is scrubbed and clearly framed before it appears in a report or reaches an AI assistant, so a hostile page cannot inject instructions.

Evidence

A Re-Checkable Receipt

"We checked it" is not evidence. A compliance team, an auditor, or a future developer needs to confirm for themselves that a specific change was tested before it shipped.

When a run passes with no new barriers, usabl writes a small receipt that records what made the result reproducible: a hash of the source tree, a hash of the committed policy, and the exact scanner versions. Because the policy is read from the commit rather than a working copy, and the scanner versions are pinned, the same commit produces the same verdict every time.

Summary

Continuous Accessibility Verification

usabl moves accessibility checking into the everyday workflow, the CLI, CI, and AI assistants, instead of a separate audit that happens later.

It records existing issues as a baseline, blocks only new ones, and points the same engine at both the application and its documentation. Teams can change the UI, and the docs, knowing nothing new slipped through.
