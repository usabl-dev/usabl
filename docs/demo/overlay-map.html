usabl dev-server overlay: the files and how they interact

The overlay is the accessibility inspector that appears inside a running Vite app. This page names every file that takes part, in the app and in the engine, and follows one scan from a page load to the panel. The panel never decides anything. It shows the result the gate produced.

One scan, left to right

Three lanes: the browser where the developer works, the Vite dev server with the usabl plugin loaded, and the engine the plugin calls. Numbered arrows match the list under the diagram.

Page load

Page opens

You open http://127.0.0.1:5173/. Vite serves your app's index.html.

1

transformIndexHtml adds a loader

One small script tag. If the browser is not automated and the address does not carry ?usabl=off, it imports /__usabl/client.js.

The engine is not involved yet.

Panel script boots

Draws the usabl launcher in a corner, inside a shadow root so the app's styles cannot reach it. Captures the page's own fetch before later scripts can replace it. That is hardening, not a boundary: the panel runs in the page's realm, so when it finds a global already replaced it says so in the panel instead of presenting the result as trustworthy.

2

GET /__usabl/client.js

The plugin serves the panel source from src/surfaces/overlay-client.ts, with two lines in front that open a Vite hot context so the panel can hear the refresh event. Both /__usabl endpoints refuse any request that does not come from the dev origin.

Still no engine work.

The scan

Panel asks for the result

Sends GET /__usabl/result with the page's native fetch.

3

Result cache

Serves the last result if nothing changed. Otherwise starts one engine run. A second request joins the run in flight instead of starting another.

4

loadConfig, then buildDeps

Reads usabl.config.json, then assembles the run: a git reader, a file reader, the provider stack, version stamps for the runner and the scanners, and the saved session named by USABL_STORAGE_STATE when one is set. It does not launch a browser here. The plugin hands it the one Chromium it keeps warm for the dev session.

While the run is in progress the panel replaces the verdict word with Scanning and keeps the previous result's findings, coverage, and receipt on screen.

The plugin waits for the run. Nothing is computed on the server side except the call itself.

run(deps, config): the gate

  • Asks git which files changed, maps them to screens through the config.
  • Opens each affected screen at appBaseUrl. That browser is automated, so it never sees the panel.
  • Runs axe, the PatternFly rules, and the keyboard walk.
  • Weighs findings against the evidence floor and waivers: new, carried, or waived.
  • Returns one Result, with a receipt when the verdict is verified.

Panel renders

Verdict, coverage, findings split by the screen you are on, and the receipt. This screen's findings split again into barriers that block the run and debt already recorded. Offers Highlight it, Move focus to it, Open in editor, and Check again.

6

projectOverlay seals the result

Runs the scrubber: control characters stripped, credential-shaped text redacted, page text wrapped in the untrusted frame. Marks the payload advisory with exit code 0, then answers as JSON.

5

Result

The same object usabl check prints in the terminal and the Stop hook reads.

Keeping it current

You save a UI file

For example src/pages/Clusters.tsx. The page hot-reloads as usual.

7

File watcher

On change, add, or unlink: clears the cache straight away, then waits 80 ms to group a burst of saves before sending the usabl:refresh event over the dev socket. Clearing first is deliberate. Clearing at the end of the wait left a window where a read could still be handed the tree from before the save. The panel hears the event and repeats step 3.

A new run starts only when the panel asks again.

Check again

The button in the panel. Sends /__usabl/result?fresh=1.

8

fresh=1 skips the cache

The one user-driven way to force a run. It still joins a run already in flight rather than starting a second one.

Runs the gate again, same as step 4 and 5.

Findings arrive with a file and line, so the panel can name the exact place to edit.

9

transform adds source markers

In the dev server only, src/surfaces/vite-jsx-source.ts adds data-source-file and data-source-line to JSX tags. The scan reads them back from the page.

This is why a finding can point at Clusters.tsx:26.

How to read the diagram

  1. Page load. Vite serves the app and the plugin's transformIndexHtml hook adds one loader line to the HTML.
  2. Panel source. The loader imports the panel from the plugin's own endpoint. Automated browsers and ?usabl=off skip this step, so usabl never grades its own badge.
  3. Ask for the result. The panel requests the result endpoint.
  4. Build the engine. On a cache miss the plugin loads the config and builds the engine's dependencies: browser, git, and session.
  5. Run the gate. The engine scans the affected screens and returns one Result. This is the same function behind usabl check, the Stop hook, and CI.
  6. Seal and show. The plugin scrubs page text, frames it as data, marks the payload advisory, and the panel renders it.
  7. Save a file. The watcher clears the cache and tells the panel to ask again.
  8. Check again. The button forces a fresh run.
  9. Source markers. A separate transform, in the dev server only, stamps file and line onto JSX so findings can point at code.

How vite.config.ts loads the plugin

Two lines in the project's Vite config do all the work. This is the whole of the app-side wiring in usabl-app:

import { usablVitePluginFromConfig } from 'usabl/vite'

export default defineConfig({
  plugins: [
    react(),
    usablVitePluginFromConfig({ cwd: import.meta.dirname }),
  ],
})
  1. npm run dev starts Vite. Vite compiles vite.config.ts and runs it once, before it serves anything.
  2. The import resolves through the package. Node looks up usabl in node_modules/usabl. In usabl-app that is a symlink to the sibling engine folder, created by the "usabl": "file:../usabl" dependency. The engine's package.json maps the ./vite export to dist/vite-plugin.js. The app runs whatever build sits in that folder, so an old engine build shows an old panel until you rebuild the engine and restart the dev server.
  3. The function call builds a plugin object. It records the folder you pass as cwd, resolves usabl.config.json inside it, and prepares one shared headless browser that launches lazily on the first scan. It returns an object named usabl-overlay with enforce: 'pre' and five hooks: configResolved, configureServer, transformIndexHtml, transform, and closeBundle. No scan happens at this point.
  4. Vite calls the hooks at the right moments. configResolved runs first and settles two things: whether source markers are switched on at all, by checking that Vite's command is serve, and which host and port the origin check will accept. At server start, configureServer registers the two /__usabl endpoints and the file watcher listeners. When a browser asks for the page, transformIndexHtml adds the loader line. For each JSX or TSX module, transform stamps the file and line markers. When the server stops, the warm browser is closed, with closeBundle as the backstop for hosts that run Vite in middleware mode and never expose a server to listen to.
  5. The first scan waits for the browser. Only when the panel requests /__usabl/result does the plugin's run function load the config, build the engine's dependencies, and call the gate. Each run reads the config and the session again, so exporting a new session or editing the config takes effect on the next scan without a restart.

Two details matter in practice. The cwd you pass is where the config is read from. The ansible-ui demo keeps its Vite config under platform/, so it passes the parent folder. And enforce: 'pre' places the plugin before React's transform so the source markers see raw JSX. That ordering breaks generic JSX type arguments in ansible-ui, so that app spreads the plugin with enforce: undefined and gives up line numbers there.

Installing it: usabl install --overlay

Run the installer once, from the folder that holds the project's Vite config:

usabl install --overlay

It looks for a Vite config in the folder you run it from, with no search of parent or child folders, trying vite.config.ts and then the .js, .mts, .mjs, .cts, and .cjs variants in that order. It then takes one of three paths. It never edits an existing file.

No config exists

Writes a new vite.config.ts with the import, the plugin entry, and a comment explaining what the plugin is. Prints "Wrote vite.config.ts with the usabl overlay plugin. Review this draft before you merge it."

Config already loads the plugin

Detects the import and the call, ignoring comments and strings, and prints "already wires the usabl overlay plugin. No change." Safe to run again at any time.

Config exists without the plugin

Refuses, because it cannot prove a lossless insertion into a hand-tuned config. Prints the exact import line and the exact plugins entry to add by hand, the same two lines shown above.

The draft it writes when no config exists:

import { defineConfig } from 'vite'
import { usablVitePluginFromConfig } from 'usabl/vite'

// usabl overlay wiring. This plugin projects the gate-owned Result inside the dev server
// as an advisory badge. It never changes exit codes: usabl=off and webdriver runs skip it.
export default defineConfig({
  plugins: [
    usablVitePluginFromConfig({ cwd: import.meta.dirname }),
  ],
})

After wiring, restart the dev server. Vite loads plugins once at startup. usabl doctor reports the overlay as wired when it finds the import and the call in a root Vite config. It reports the overlay as missing on a project whose Vite config lives in a subfolder, such as the ansible-ui demo, even when the plugin is wired there by hand. In that case the proof is the running server answering /__usabl/client.js and /__usabl/result.

The installer lives in src/install/overlay.ts. It is one of seven install targets. The other six are --claude for the Claude Stop hook, --claude-skill for the two Claude skills /usabl-check and /usabl-fix, --cursor for the Cursor hook and its adapter, command, and rule, --ci for the gate workflow, --docs-ci for the docs gate workflow, and --branch-rule for a read-only branch protection check.

The engine files behind it

FileOwns
src/surfaces/vite-plugin.tsThe plugin. Serves the two endpoints, keeps the result cache, watches files, sends the refresh event, injects the loader, and refuses requests that do not come from the dev origin. Also owns the browser: one Chromium, launched on the first scan and reused for the whole dev session, closed when the server stops. Exports usablVitePluginFromConfig, which is what vite.config.ts imports as usabl/vite.
src/surfaces/overlay-client.tsThe panel itself, shipped as a string and served as JavaScript. Isolated in a shadow root. Holds the launcher and inspector, the per-screen split of findings, the four-corner dock that moves itself out of the way when you ask to see an element it covers, the status-aware "How to fix it" detail, Highlight it, Move focus to it, Open in editor, Check again, the refresh listener, and the focus management and live regions that let the panel itself be operated by keyboard and screen reader.
src/surfaces/vite-jsx-source.tsThe transform that stamps file and line onto JSX opening tags, in the dev server only. It runs before the host JSX transform. On code with generic JSX type arguments it can break the build, which is why the ansible-ui demo places the plugin after React and gives up line numbers there.
src/surfaces/scrub.tsStrips control characters, redacts credential-shaped values, removes frame markers from page text, and wraps page-derived strings in the untrusted frame.
src/install/overlay.tsThe installer behind usabl install --overlay. Writes a draft config when none exists, reports no change when already wired, and refuses to edit a hand-tuned config.
src/run.tsThe gate. One function, called by every surface.
src/output/disclosure.tsOwns isBlockingBarrier, the single rule for whether a finding blocks. The panel does not copy this rule, it carries the function itself into the browser as source.
src/deps/build.tsAssembles everything one run needs: the git reader, the file reader, the provider stack, the clock, version stamps for the runner and the scanners, and the session read from USABL_STORAGE_STATE. It can launch its own Chromium, but on the overlay path it does not, because the plugin passes in the browser it already keeps warm.
src/cli.tsProvides loadConfig, the same config reader the terminal uses.
dist/vite-plugin.jsThe built bundle that the usabl/vite package export resolves to. Rebuild the engine and restart the dev server to pick up a change.

Boundaries worth saying out loud

Advisory by construction

The panel has no way to write anything. It only asks for JSON the gate produced, and that payload is marked advisory with a display exit code of 0, even though it also carries the gate's real verdict and exit code so the panel can show them. The panel does sort, group, and count what it is given, but nothing it works out is fed back to the gate. The terminal command, the Stop hook, and CI are the surfaces that can block.

A run that fails says so

If the run throws, the endpoint answers 500 and the panel says it could not load the current result and points at the dev server log, which is where the reason is written. The reason stays on the server, because a failure can carry absolute paths and config detail. A failed run is never presented as a run still in progress, and it is never cached, so the next read tries again.

One definition of what blocks

The panel does not decide which findings are barriers. It carries the gate's own isBlockingBarrier function into the browser as source text, so its "barriers" and "recorded, not blocking" lists cannot drift from the gate's rule. This is a repaired defect, not a precaution: the panel used to split findings without reading their status, and so offered "How to fix it" for debt the gate had already accepted.

usabl never grades its own badge

The scanner's browser is automated, so the loader skips the panel inside scanned pages. The findings you see describe your app, not the inspector.

Page text is sealed

Anything read from the page reaches the panel, and any assistant, inside a labeled frame that marks it as data. The page cannot close that frame, because the markers are stripped out of page text before the frame is put around it.

A name collision

src/intake/overlay-fs.ts shares the word overlay but is unrelated. It layers requirement files for the intake step.

What needs a restart, and what does not

Vite loads plugins once at startup, so editing vite.config.ts or rebuilding the engine needs a dev server restart, plus one hard reload so the browser fetches the new panel script. Editing usabl.config.json does not. Every run reads it again, so the change lands on the next scan.

Where the config lives matters

The plugin reads usabl.config.json from the folder you pass as cwd. The ansible-ui demo keeps its Vite config under platform/, so it passes the parent folder.
