1What usabl does

When someone changes a UI, or edits a page of the product's own documentation, usabl checks whether that change introduced a new accessibility problem - the kind a machine can catch without human judgment. It returns one of four answers:

AnswerPlain meaningWhat happens
verifiedThe screens you touched have no new machine-detectable barriers.Work proceeds.
regressionYou introduced a new problem.Blocked until fixed.
not_coveredusabl could not figure out which screens your change affects, so it cannot vouch for anything.Blocked by default (configurable).
approval_requiredYou changed usabl's own policy files. It refuses to judge changes to itself.Blocked until a human approves.
idleYour change did not touch any UI. Nothing to check.Work proceeds (this is not a verdict).

The core idea: Existing tools find problems and list them. usabl goes further - it makes a pass/fail decision and can stop an AI coding assistant from calling work "done" until the new barriers are gone. The AI can suggest fixes, but it cannot mark its own homework.

How it works

There is one engine that does the actual work: figure out which screens changed, run the checks, decide the verdict. The CLI (usabl check) is the main way to call it. Every other surface calls the same engine underneath - they just trigger it from different places:

  • Stop hook - blocks the AI assistant from finishing
  • Browser overlay - shows findings while you develop
  • CI comment - posts the verdict on a pull request
  • Mid-task self-check - the AI checks its own progress partway through
  • Playwright helper - for test suites
  • Reports - generates accessibility artifacts

None of these surfaces have their own verdict logic. One engine, one answer. Only findings the machine can prove (deterministic evidence) affect the verdict. Softer checks can be shown as advice but never block.

Two surfaces, one engine: app and documentation

usabl checks two target surfaces, not one. The application UI is the original surface. Since v0.2.1 the same engine also checks the product's own published documentation, the user guides and install docs. Those pages carry the same accessibility barriers as the app and almost never get tested.

Documentation checking is not a second product or a separate command. One usabl check run scans both surfaces and returns one verdict. It works like this:

  • Turned on by a manifest. A usabl.docs.json file lists the doc pages to check. No manifest, no docs surface.
  • Same checks, doc-appropriate. axe-core runs against the WCAG 2.2 AA rule set and a docs rule catches broken heading order. The PatternFly rules are skipped, since product docs are not PatternFly.
  • Fixes land in the writer's source. A finding on a rendered page is traced back to the AsciiDoc source, so a writer sees the fix in their own markup, not a browser selector.
  • Same coverage discipline. Only changed pages are re-checked, and a doc source it cannot map is an honest not_covered, never a silent pass.

What we are building for the contest

The full verdict engine, three scan layers (axe-core for general a11y, a PatternFly-specific rulepack, and a keyboard walk), all the surfaces listed above, design intake (so designers can declare intent in YAML), accessibility reports, and accessibility checking for the product's own documentation pages (added in v0.2.1). Not building: IDE extensions. Optional: an MCP wrapper for the mid-task check.

How much of "accessibility" this covers

WCAG 2.2 Level A+AA has 55 criteria. usabl does not cover all of accessibility - it covers what a machine can prove, on the screens it checked. Here is the honest breakdown:

CategoryCount% of A+AA
Contest scope (deterministic, machine-checkable)2138%
Stretch (visible focus, if time)12%
Post-contest (deterministic, buildable later)1324%
Advisory (AI judgment, shown but never blocks)47%
Not applicable (media in admin consoles)47%
Never (requires human judgment or application logic)1222%

What we say: usabl mechanically verifies 21 of 55 criteria at contest time (38%). With post-contest providers built out, 35 of 55 (64%). The remaining 16 are either not applicable to admin consoles or require human judgment the tool will never replace.

What we do not say: "usabl makes your app WCAG compliant." It does not. Compliance requires all criteria including the ones only a person can judge. We also do not say "covers X% of accessibility" - WCAG is not the whole of accessibility.

How it stays honest

Two layers of protection, with different strength:

  • On the developer's machine: usabl watches its own config files. If someone edits the rules to cheat, the tool notices and flags it. It cannot physically prevent the edit, but it can refuse to issue a clean verdict afterward.
  • In CI (pull requests): The CI job reads usabl's policy from a protected branch, not from the PR itself, so the PR cannot weaken its own checks. This is the strong layer.

3Open decisions

These are the things the ground truth deliberately leaves open. Each needs a decision before work can proceed past it.

DecisionWhat it means and why it matters
Which app and bug for the live demo Pick the PatternFly app the demo runs on and the one accessibility bug the AI will fix live. Lock both before anything else, because the screen-reader recording has to match this exact bug. If the bug changes after recording, the audio is wrong.

Options for the hero bug:
  • Modal focus return (rule 2, Clusters page). Visible on screen (focus jumps to the wrong place), audible in the transcript (wrong element announced after Escape), and the fix is a single returnFocus prop. Short enough for a live loop.
  • Toast with no live region (rule 4, Clusters page). Strong empathy - the success message is completely silent to a screen reader. But the fix is slightly less visible on screen.
  • Kebab toggle missing name + expanded state (rules 1+3, Clusters page). Two findings on one control, shows multi-layer detection. Risk: two fixes in the demo loop takes longer.
Recommendation: Modal focus return. One clear bug, one clear fix, maximum audio contrast between "before" and "after."
Which rules make the cut (validate against real data) The eight PF rules are a starting set. The ground truth says: gather 20-50 real accessibility bugs, run the current rules against them, and count how many get caught. If a bug pattern shows up repeatedly and no rule catches it, that rule goes to the top of the backlog - potentially replacing one of the structural rules (6-8).

This means the final rulepack is data-driven. We might have access to a customer bug database that changes the picture entirely.

Options:
  • Collect the bug sample first, then lock the rules (or swap). Run the sample before building rules 6-8. If a structural rule catches nothing real but a different pattern catches ten bugs, swap it. Risk: delays rule work by a day or two.
  • Build rules 1-5 now, validate 6-8 against the sample. The five interaction rules carry the demo and are unlikely to be displaced. Only the structural three are at risk. Build 1-5 while gathering the sample, then decide 6-8.
  • Lock all eight, use the sample for the pitch number only. Build everything listed. The sample becomes evidence for judges ("caught 22 of 30"), not a selection mechanism. Risk: a rule that catches zero real bugs weakens the pitch.
Recommendation: Build 1-5 now. Gather the bug sample in parallel. Validate 6-8 against it before building them. Zero cost to the critical path, and the pitch number stays honest.
Which real app to run the honest test against Separately from the demo fixture (which we control), pick a real PatternFly codebase to run usabl against. This produces the honest numbers: how well does the tool work on code that was not written for it?

Options:
  • OpenShift console. Large, real, internal credibility. PF v4/v5 mix. High route count tests coverage at scale. Risk: may need import alias resolution or not_covered rate will be high.
  • PatternFly React demos or patternfly.org. Canonical PF usage, no alias tricks. Risk: too clean, may not produce enough findings to be interesting.
  • A mid-size PF console (e.g. Hybrid Committed Cloud). Smaller, less setup, still real. Risk: less name recognition for judges.
Recommendation: OpenShift console. Judges know it, the large surface proves coverage works at scale, and honest numbers on a hard target are more credible than easy numbers on a simple one.
What coverage number to put on the slide The "verified-verdict-rate" is the share of UI-touching changes that get a clean verified result. We measure it on the real app and report whatever we get. The question is how prominently to feature it.

Options:
  • Headline it on the proof slide, whatever the number is. If above 70%, it speaks for itself. If below, pair it with the discovery roadmap and frame as "here's today, here's what's next."
  • Lead with something else, footnote the coverage number. Lead with false-positive rate (zero on clean markup) or time-to-fix. Coverage in fine print. Works better if the number is mediocre.
  • Decide after measurement. Do not commit to slide position now. Run the measurement in week 2, then pick framing based on the actual number.
Recommendation: Decide after measurement. Commit now only to reporting honestly. If it is strong, promote it. If weak, pair with the explanation.
Can the repo block merges, and what if it cannot Our repo is private on GitHub Free. GitHub Free does not let you require a status check to pass before merging. So right now, usabl's CI verdict can post a comment saying "this PR has a regression," but nothing actually prevents someone from clicking Merge anyway.

This matters because the product story is about stopping bad code from shipping. If we cannot demonstrate an actual block, we have to explain the gap.

Options:
  • Make the repo public now (already Apache-2.0). Public repos on Free get required checks, CODEOWNERS, and branch protection. Also makes the contest submission obvious. Risk: code visible before it is polished.
  • Stay private, accept comment-only for now. CI still runs, still posts the verdict. Demo shows the comment and explains "one toggle away from blocking on a public or Team repo." No cost, no exposure.
  • Pay for GitHub Team. Required checks on private repos. Real money for a contest. Probably overkill.
Recommendation: Stay private during build. Go public when ready for submission. Gets required checks for the demo, aligns with the open-source positioning, costs nothing.
Where do the real bugs come from We need 20-50 real accessibility bugs to validate the rulepack and produce the "caught N of M" number for judges. Need to decide what sources to pull from and who gathers them.

Options:
  • PatternFly GitHub issues (a11y label). Public, citable, no approval needed. Skewed toward component-level bugs. Good for rulepack validation.
  • Internal product bugs (Jira/Bugzilla, anonymized). Richer composition bugs (modals, tables, toolbars). Closer to what usabl's PF rules target. Needs permission and anonymization.
  • Both, deduplicated. 15-20 from PF GitHub, 15-20 from internal, merged. Best coverage of both patterns.
Recommendation: Both sources. Start with PF GitHub (no approval needed, can begin immediately). Add internal bugs as they clear. Report the split honestly.
Whether to build the MCP version The mid-task self-check already works as a CLI command. MCP is a second delivery mechanism that makes the AI more likely to discover and run the check on its own. The trade-off: MCP is another path to build, test, and secure. It passes page-derived text (aria-labels, headings, error messages) into the AI's context as structured data, which is a prompt-injection surface the CLI path avoids.

Options:
  • Skip MCP. CLI only. Simplest. One fewer thing to build and secure. Demo works fine - the agent runs usabl check on screen.
  • Build MCP as a stretch goal after the core loop is solid. Gate it on hero-loop readiness, not on a date.
  • Build MCP early because testing shows the AI forgets to self-check. Only if rehearsals reveal the model never calls usabl check unprompted without tool registration.
Recommendation: Skip unless rehearsals show the model fails to self-check via CLI. The demo does not depend on MCP, and the security surface is real work.

4Discussion points

These are not decisions with clean options - they are things that need a conversation because the doc leaves a real choice, links people's work, or carries risk.

  1. The data shapes freeze is hard to undo. The plan is: freeze all the shared types on day 1, then two people build separately (one builds detection, one builds the verdict engine) until they join up at integration. If a type is wrong, both people find out late. Hold a focused review of every shared type before locking. The test person should be in that review because the honesty guarantees depend on these shapes.
  2. The not_covered blocking behavior is deliberately unresolved. By default, if usabl cannot figure out which screens changed, it blocks. But if measurement on a real app shows this happens a lot (say, more than 10% of runs), it should probably warn instead. Agree on the threshold now and who makes the call, because this is the item most likely to cause arguments if the real app scores badly.
  3. Coverage discovery is the main technical risk. The tool figures out which screens a change touches by reading imports and routes. It will miss: path aliases (@/, ~/), dynamic imports, routes built from data, and some edge cases around comments. On a real PatternFly app these are common. The backup plan is to read routes from the running app instead of parsing source. Agree what triggers that and who builds it, because it steals time from rule-building.
  4. The screen-reader recording is a dependency, not a task. The demo app and the hero bug must be locked before the recording happens. If the app or bug changes after recording, the audio is wrong. The person building detection and the person doing the recording need to agree a hard freeze point. This links two people's work across teams.
  5. The spoken-text preview is an approximation, and a judge could catch it. usabl builds its transcript from the accessibility tree, not from a real screen reader. One value (aria-sort) is read straight from the HTML because the tool cannot get it the normal way. The doc says: disclose this, do not hide it. Before recording, confirm the preview matches what a real screen reader actually says for the demo bug. Make sure aria-sort is the only exception.
  6. Keep the test fixture honest. The demo app has a clean mode (zero findings) and a broken mode (exactly N findings, matching the rule count). If either drifts, the test harness is lying. The stretch checks (visible focus, reduced motion) must never go into this fixture. Everyone adding a rule needs to know this.
  7. Idle vs not_covered must live in one place in the code. The doc is firm: "nothing to check" (idle) and "could not figure out what changed" (not_covered) must never share a code path or a verdict. This is the kind of thing two people build slightly differently. Write it once, in one place.
  8. Design intake needs a real example, not just a schema. The ground truth defines the TypeScript interface and one example per assertion type, but it does not show what a designer's actual YAML file looks like in practice. Decisions:
    • What does the YAML a designer writes actually look like? A working example needs to exist before the schema is locked.
    • Does an intake-derived check appear in the demo? If yes, put a requirement file in the fixture app. If no, intake is proven by tests only.
    • Who validates the full path from YAML file through normalize through to a finding that participates in the verdict?
    Options:
    • Ship one working example in the fixture app. A single assertion ("this image must say X") that the broken variant gets wrong. Proves the path end-to-end.
    • Prove intake in tests only, skip it in the demo. Less to show, one fewer thing to break live.
    • Defer intake wiring to post-demo. Build the schema, skip the runtime integration. Risk: the "designers declare intent" story is unproven.
    Recommendation: Ship one working example. Low effort (one YAML file, one planted mismatch), proves the path, and gives the demo an optional beat.

5Work split

Three people write code. One is more focused on testing but still ships code. The other roles (screen-reader recording, demo video) belong to other people and are not part of this split.

Person 1: verdict engine + surfaces
The verdict engine (gate), coverage, integrity guard, receipts, the CLI, and the stop hook. These parts are tightly linked and must be correct, so one person holds all of them.
Person 2: detection + design intake
The three scan providers (axe wrapper, PatternFly rulepack, keyboard walk), the demo fixture app and its oracle, the real-bug sample, and design intake (schema, YAML reader, intake-derived checks). Intake lives here because it produces the same kind of output as the scanners.
Person 3: testing, performance, security
Integration tests, performance work, CI setup, the honesty audit, and the security tests that try to break the tool. Also reviews the other two people's code.
Not in this split The demo video and the live screen-reader recording belong to other people. But you have to feed them: lock the demo app and hero bug early so the recording can happen. Save raw demo runs as you go.
Watch this The doc protects both the overlay and Reports from being cut. With only three people writing code, that is a lot of surface. Agree now which of those two slows down first if you fall behind, so it is a decision and not a surprise.
Key dependency Person 1 (verdict engine) and Person 2 (detection) build separately using the shared types, then join up at integration. A wrong type is expensive. That is why the kickoff puts the data shape freeze first.

6Kickoff agenda

Leave this meeting with: the shared types locked, the work divided, and the must-be-first steps sequenced. Everything else can wait.

  1. Divide the work. Quick.
    Decide who takes each of the three lanes above. Make sure one person (not several) owns the verdict engine, and one person owns the fixture and its oracle. Agree which of the overlay or Reports slows down first if you fall behind.
  2. Lock the shared types. This is the most important item.
    Go through every shared type: Draft, Finding, Result, Coverage, Receipt, and the identity fields. Both the detection person and the verdict-engine person must agree. Nail down two things:
    • Idle (nothing to check) and not_covered (could not identify what changed) are handled in exactly one place and never confused.
    • Only deterministic findings reach the verdict. The gate filters everything else before deciding.
    Lock at the end of this item. Changing later costs both builders.
  3. Sequence the blockers. Medium.
    Some things have a required order:
    • Pick the demo app and hero bug, lock them, then the screen-reader recording can happen. Tell the recorder early - they are outside this meeting.
    • Pick the real app, run usabl against it, read the not_covered rate, then decide whether it blocks or warns.
    • Confirm the repo situation: comment-only for now, go public at submission.
  4. Assign the honesty check. Quick.
    One person owns this before recording: confirm the spoken-text preview matches a real screen reader for the hero bug, confirm aria-sort is the only value read straight from HTML, and make sure the disclosure is in the submission.
  5. Confirm the cut order. Quick.
    Cut rules 8, 7, 6 first. Then MCP. Then stretch goals. Never cut: the verdict engine, the receipt, the integrity guard, CODEOWNERS, the four verdicts, the transcript diff, the hero loop, the overlay, Reports, and the CLI self-check.
